# Krakow Tram Quiz

A game for transit nerds. Given a start and end stop, pick which tram lines to take — in order — to get there with fewest stops.

---

## Core loop

```
1. Pick difficulty → random unsolved challenge appears
2. See: "From Plac Centralny → Kampus UP JP II"
3. Tap line chips to build route: [52] → [10]
4. Map draws those lines live as you add them
5. Submit → BFS computes optimal → correct / incorrect + optimal shown
6. Challenge marked solved in localStorage → next
```

---

## Difficulty

| Level  | Transfers | Lines in solution |
|--------|-----------|-------------------|
| Easy   | 0         | 1                 |
| Normal | 1         | 2                 |
| Hard   | 2+        | 3+                |

Future mode selector: **Trams only → Trams + buses → Trams + buses + aglo buses** (same engine, wider network graph).

---

## Anti-cheat: no stored answers

Challenges are hardcoded as `{id, from_stop_id, to_stop_id}` only — **no correct answer stored anywhere**.

On submit, BFS runs in-browser on `network.json` to compute the optimal route, then compares against the user's pick. Cheating requires intercepting and understanding the BFS output — more effort than knowing the tram network. Hashing was considered but rejected: with 23 lines and ≤3 transfers, all ~12 000 combinations can be brute-forced in milliseconds, making any hash trivially reversible.

Progress (which challenge IDs are solved) stored in `localStorage`.

---

## Transfer UI

User taps **line chips only** — no transfer stop selection. Order matters (`52 → 10` ≠ `10 → 52`). This sidesteps the "two lines sharing a long common section" ambiguity — the engine finds the optimal boarding/alighting point automatically via BFS.

---

## Map

Always visible. Renders only the lines the user has added to their current answer. Updates live on each tap (add/remove line). On submit, switches to showing the optimal route.

---

## Scoring

Binary: **Correct** (matched optimal stop count) or **Incorrect**. No points, no timer. After result, optimal route is revealed regardless of outcome.

Multiple valid shortest paths are all accepted — BFS checks stop count, not the specific sequence of stops.

---

## Data

```
build.py reads GTFS_KTK_T.zip → public/data/
  network.json     – {route_id: {name:"52", stops:[stop_id,...]}, ...}  both directions
  stops.json       – {stop_id: {name:"Plac Centralny", lat, lon}, ...}  directional pairs merged by name
  challenges.json  – [{id, from_stop_id, to_stop_id, difficulty:"easy"|"normal"|"hard"}]
```

No correct answers in any file. `challenges.json` is generated by build.py: run BFS across stop pairs, bucket by transfer count, sample interesting pairs (avoid trivial same-line endpoints, prefer well-known stops).

---

## Pathfinding

BFS on a graph where nodes = logical stops, edges = (stopA → stopB, route R, cost = 1 stop).

Used for:
- Generating challenges at build time (bucket by difficulty)
- Validating user answer at submit time

Graph is small (~500 stops, 23 routes) — runs in-browser in <10 ms.
